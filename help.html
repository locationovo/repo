Q: 为什么不支持 Cydia？

A: 本源采用现代 APT 高级源结构（Structured Repository），并使用了 GPG 签名保护。Cydia 的设计较为陈旧，存在以下兼容性问题：

  • Cydia 无法自动识别并导入本源的公钥（key.gpg），会提示“未签名”或“签名无效”。
  • Cydia 对 dists/stable/main/binary-iphoneos-arm64/ 等结构化目录的解析极不稳定，容易刷新失败。
  • Cydia 已多年未更新，对新设备和新越狱环境（如 rootless、roothide）的支持很差。

建议使用 Irisin 或 Sileo 等现代包管理器，它们能完美支持本源的签名和高级源结构。

Q: 如何添加本插件源？

A: 点击主页上对应的按钮即可一键添加：

  • Irisin：点击后会自动打开添加面板，确认即可。
  • Sileo：点击后会跳转到 Sileo 的添加页面，确认即可。
  • 也可以点击“复制源地址”，然后在包管理器中手动粘贴添加。

Q: 为什么刷新源很慢或失败？

A: 本源的索引托管在 GitHub Pages（*.github.io）。由于该域名在国内直连不稳定，建议：

  • 开启代理，并将 *.github.io 加入代理规则。
  • 若使用 Irisin，可在设置中适当调大源的超时时间。

Q: 主源、镜像源和这些包到底是怎么运作的？

A: 本越狱源的架构设计为“轻量索引，重物分离”，以避免 Git 仓库超载：

  • 主源（本页面所在源）：仅作为索引聚合器，不存储任何 .deb 文件。它通过 GitHub API 自动抓取各个子仓库的元数据生成索引。
  • 自主编译包：由我的 recipes 仓库从源码编译打包，作为资产发布在 GitHub Releases 中。
  • 修补历史包（Procursus / Bingner）：很多旧版插件仅支持 rootful 环境，直接安装会报错。我的 patched-legacy 仓库会下载这些原包，通过自动化工具重写二进制加载路径（修复 dylib 报错），然后将修补后的包同样作为资产发布在 GitHub Releases 中（若修补失败则保留原包）。

当您在客户端点击安装或下载时，无论是我编译的还是修补的，都是通过 GitHub Releases 的高速 CDN 获取，而不是直连原作者的服务器。这使得旧插件能在现代越狱环境下被研究和使用。

Q: 为什么包是通过 Releases 下载的？

A: 为了避免 Git 仓库体积膨胀（GitHub 限制单仓库 1GB），本源的软件包（包括我编译的插件和修补的历史包）均作为 GitHub Release 资产托管。主仓库仅保存轻量的文本索引。

Q: 什么是“修补的”历史包？

A: 很多优秀的旧插件仅支持 rootful 环境，直接安装会报错。本源使用自动化工具重写了包的二进制加载路径，使其能在现代 rootless 环境下运行。若修补失败，将回退至原始包。不保证所有旧插件都能完美运行。
